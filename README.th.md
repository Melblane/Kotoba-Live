# Kotoba Live

ซับไตเติลภาษาญี่ปุ่นเป็นภาษาไทยแบบเรียลไทม์ สำหรับเสียงที่กำลังเล่นอยู่ในแท็บเบราว์เซอร์ คุณเลือกแท็บหรือหน้าต่าง จากนั้น Kotoba Live จะฟังเสียง ถอดเสียงภาษาญี่ปุ่น แปลเป็นภาษาไทยแบบสำนวนพูด แล้วแสดงผลเป็นซับไตเติล ใช้ได้ดีกับอนิเมะ ละคร ไลฟ์สตรีม และวิดีโอทั่วไป

```
 เสียงจากแท็บเบราว์เซอร์
        │  getDisplayMedia (เลือกแหล่งเสียงในหน้าต่างของเบราว์เซอร์เอง)
        ▼
 AudioWorklet  ── โมโน 16 kHz เฟรม PCM ละ 100 ms ──►  WebSocket  ──►  เซิร์ฟเวอร์ Node
                                                                          │
                         AudioSegmenter: ช่วงหยุดพูด, จำกัดความยาว, ส่วนซ้อนทับ
                                                                          │
                  speech-to-text (ข้อความสดระหว่างพูด, ข้อความสุดท้ายเมื่อหยุด)
                                                                          │
                     แยกประโยค (。！？, วลี) + ตัดส่วนที่ซ้ำจากการซ้อนทับ
                                                                          │
              TranslationScheduler: แปลพร้อมกัน, เรียงลำดับ, บริบท + glossary
                                                                          ▼
 ประวัติ (ทุกบรรทัด)  ◄── events ──►  คิวซับไตเติล (สิ่งที่อยู่บนจอตอนนี้)
                                          stage · overlay ลอย · Picture-in-Picture
```

## เริ่มต้นใช้งานอย่างรวดเร็ว

ต้องใช้ Node 20.6 ขึ้นไป และเบราว์เซอร์ Chromium บนเดสก์ท็อป (Chrome หรือ Edge)

```bash
npm install
cp .env.example .env      # แล้วใส่ API key ของคุณ ดูรายละเอียดด้านล่าง
npm run dev               # http://localhost:5173
```

เปิด http://localhost:5173 คลิก **Select Window / Tab** เลือกแท็บที่เล่นวิดีโอ ติ๊ก **Also share tab audio** แล้วกด **Start Listening**

ถ้าต้องการรันแบบโปรเซสเดียวสำหรับ production ให้ใช้ `npm run build && npm start` แล้วเปิด http://127.0.0.1:8787

ยังไม่มี API key? แอปยังเปิดได้ คลิก **Try demo data** เพื่อดูหน้าตาแอปพร้อมบรรทัดตัวอย่าง บรรทัดเดโมจะมีป้ายกำกับเสมอ และจะไม่ถูกรวมเข้าไฟล์ที่ส่งออก

## การตั้งค่า

key เก็บอยู่ในไฟล์ `.env` ฝั่งเซิร์ฟเวอร์ และจะไม่ถูกส่งไปยังเบราว์เซอร์ ทั้งสองบริการใช้ API แบบเข้ากันได้กับ OpenAI คุณจึงชี้ไปยังผู้ให้บริการหลายเจ้าได้

| ตัวแปร | หน้าที่ | ตัวอย่าง |
| --- | --- | --- |
| `STT_BASE_URL`, `STT_API_KEY`, `STT_MODEL` | การรู้จำเสียงพูด (`/audio/transcriptions`) | OpenAI `whisper-1`, Groq `whisper-large-v3-turbo` ที่ `https://api.groq.com/openai/v1`, เซิร์ฟเวอร์ faster-whisper หรือ whisper.cpp ในเครื่อง |
| `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` | การแปล (`/chat/completions`) | OpenAI `gpt-4o-mini`, Groq, OpenRouter, Ollama |
| `OPENAI_API_KEY` | ทางลัดเมื่อใช้ OpenAI ทั้งสองงาน | |
| `ACCESS_TOKEN` | ต้องใส่โทเคนก่อนจึงเริ่มเซสชันได้ | ตั้งค่านี้ถ้าเซิร์ฟเวอร์เข้าถึงได้จากคนอื่นนอกจากคุณ |
| `HOST`, `PORT`, `ALLOWED_ORIGINS` | การผูกเครือข่าย และ origin ของ WebSocket ที่อนุญาตเพิ่ม | ค่าเริ่มต้น: `127.0.0.1`, `8787` |
| `ENABLE_PARTIALS` | ข้อความถอดเสียงสดบางส่วน | ตั้งเป็น `false` ลดค่า speech-to-text ลงประมาณ 4 เท่า |

เซิร์ฟเวอร์ในเครื่องมักไม่สนใจ key แต่ต้องไม่ว่างเปล่า ถ้าตั้งแค่ key ของการรู้จำเสียง คุณจะยังได้ข้อความภาษาญี่ปุ่น พร้อมแจ้งเตือนชัดเจนว่ายังไม่ได้ตั้งค่าการแปล

## วิธีใช้งาน

- **Select Window / Tab** เปิดตัวเลือกของเบราว์เซอร์และแสดงมิเตอร์ระดับเสียงสด คุณจึงยืนยันได้ว่าเสียงเข้ามาแล้วก่อนส่งอะไรไปยังเซิร์ฟเวอร์ **Start Listening** เริ่มถอดเสียง (และเปิดตัวเลือกให้ก่อนถ้ายังไม่ได้เลือกแหล่งเสียง) **Change source** สลับแท็บโดยไม่ขัดจังหวะเซสชัน
- **Stop Listening** ปล่อย media track ทั้งหมดทันที จบประโยคที่ค้างอยู่ และปิดการเชื่อมต่อ
- สถานะมี Idle, Connecting, Listening, Processing และ Error พร้อมบรรทัดรายละเอียดและปุ่มแก้ไขสำหรับแต่ละปัญหา (ไม่ได้รับอนุญาต, แหล่งเสียงไม่มีเสียง, การเชื่อมต่อขาด, ไม่มี key, โควตาเต็ม, เบราว์เซอร์หยุดการแคปเจอร์)
- ถ้าการเชื่อมต่อหลุด การแคปเจอร์จะยังทำงานต่อ และแอปจะเชื่อมต่อใหม่แบบ backoff (หกครั้ง) โดยให้ timestamp ต่อเนื่อง
- **Settings** ควบคุมเนื้อหา (ไทยอย่างเดียว, ญี่ปุ่นและไทย, ญี่ปุ่นอย่างเดียว), ขนาดฟอนต์, สี, ความทึบของพื้นหลัง, ตำแหน่ง, จำนวนบรรทัดที่แสดง, ระยะเวลาที่บรรทัดที่จบแล้วค้างอยู่ (รวมโหมด Keep subtitles longer), ข้อความญี่ปุ่นสด, ฉบับร่างภาษาไทยจางๆ (ไม่บังคับ), เลื่อนอัตโนมัติ, ค่าความหน่วง และ glossary (`田中 = ทานากะ`) ที่ช่วยให้ชื่อสม่ำเสมอ การตั้งค่าจะถูกเก็บไว้ในเบราว์เซอร์
- **History** แสดง timestamp, ปุ่มคัดลอก (ไทย หรือทั้งสองภาษา), ปุ่ม Clear ที่ต้องยืนยัน และส่งออกเป็น TXT หรือ SRT

| การแชร์ | เสียง |
| --- | --- |

| **ทั้งหน้าจอ** | เสียงระบบบน Windows และ ChromeOS เมื่อหน้าต่างเลือกมีตัวเลือกนี้ |

### ทำไมซับไตเติลลอยทับแท็บอื่นไม่ได้

เว็บไซต์ไม่สามารถวาดทับแท็บอื่นหรือแอปบนเดสก์ท็อปได้ นี่เป็นกฎความปลอดภัยของเบราว์เซอร์ Kotoba Live จึงมีสองทางเลือกที่รองรับ:

1. **In-app overlay**: แผงซับไตเติลลอยอยู่เหนือตัวแอปนี้
2. **หน้าต่าง Picture-in-Picture**: หน้าต่างที่อยู่บนสุดเสมอจริงๆ ลากไปวางทับวิดีโอได้ Chrome และ Edge 116 ขึ้นไปใช้ Document Picture-in-Picture และทำตามการตั้งค่าซับไตเติลทั้งหมด เบราว์เซอร์อื่นที่มี video PiP จะได้แบบสำรองที่เรนเดอร์ด้วย canvas โดยขนาดและตำแหน่งเบราว์เซอร์เป็นผู้กำหนด

ถ้าต้องการซับไตเติลทับแอปใดก็ได้ (รวมถึงเกมเต็มจอ) ต้องทำเป็นแอปเดสก์ท็อปแยกต่างหาก ส่วนขยายที่เหมาะสมคือเปลือก Electron ที่ใช้เซิร์ฟเวอร์นี้และคอมโพเนนต์ `SubtitleBox` ซ้ำใน `BrowserWindow` แบบโปร่งใส อยู่บนสุดเสมอ และคลิกทะลุได้ โดยรับเสียงจาก loopback ของ `desktopCapturer` ส่วนนี้ไม่ได้รวมอยู่ในโปรเจกต์นี้


## ไปป์ไลน์ทำงานอย่างไร

### สิ่งที่คุณเห็น

- **เป็นสแต็ก ไม่ใช่บรรทัดเดียว** ซับไตเติลใหม่ปรากฏที่ด้านล่างของสแต็กและบรรทัดเก่าเลื่อนขึ้น พร้อมสไลด์สั้นๆ (ประมาณ 280 ms ใช้ `transform` อย่างเดียว) และเฟด บรรทัดใหม่จะไม่ไล่บรรทัดเก่าที่ยังอ่านอยู่ออกไป บรรทัดเก่าจะจางลงเล็กน้อย
- **ทุกบรรทัดมี id คงที่** ข้อความญี่ปุ่นสด ประโยคที่จบแล้ว และคำแปลไทย อัปเดตแถวเดียวกันทั้งหมด จึงไม่มีการแทนที่หรือ mount ใหม่ ส่วนของบรรทัดสดที่รอดจากการรีเฟรชครั้งล่าสุดจะแสดงปกติ ส่วนที่ยังไม่นิ่งจะจางลง
- **สี่สถานะ:** *interim* (กำลังฟังอยู่), *translating* (ญี่ปุ่นจบแล้ว กำลังรอไทย), *final* และ *expired* (เกินเวลาอ่าน ยังคงอยู่ในประวัติ)
- **เวลาอ่านขึ้นกับความยาว** บรรทัดสั้นอยู่ราว 3 ถึง 5 วินาที บรรทัดยาวสูงสุดราว 9 วินาที (ปรับตามค่า Subtitle duration และมีเพดาน) นาฬิกาเริ่มนับเมื่อคำแปลไทยเสร็จ ไม่ใช่ตอนที่บรรทัดรอการแปล ถ้าสแต็กเต็ม บรรทัดที่จบแล้วเก่าที่สุดจะออกหลังผ่านไปอย่างน้อย 2 วินาที และบรรทัดใหม่สุดจะไม่ถูกดันออก ถ้าคำแปลหาย บรรทัดจะเลิกรอหลัง 15 วินาที
- **ประวัติเก็บทุกอย่าง** สแต็กเป็นคิวแยกต่างหาก (`web/src/lib/subtitleQueue.ts`) ที่อ่านจากประวัติเท่านั้น บรรทัดที่หายไปจากจอจึงไม่หายจากบันทึก
- **คำนึงถึงพื้นที่** สแต็กแสดงเท่าที่พอดี (ไม่เกินประมาณ 46% ของความสูงหน้าต่างสำหรับ overlay ลอย) และไม่เกินค่า Visible lines ที่ตั้งไว้ รองรับการตั้งค่าลดการเคลื่อนไหว (reduced-motion)

### เสียงกลายเป็นบรรทัดได้อย่างไร

- **เซกเมนต์ละหนึ่งวลี ไม่ใช่ทั้งย่อหน้า** การหายใจสั้นๆ ทำให้จบเซกเมนต์: 250 ถึง 500 ms ตามค่าความหน่วงที่เลือก และนานขึ้นเล็กน้อยสำหรับเซกเมนต์สั้นมาก เพื่อไม่ให้การอึกอักตัดวลีขาด เซกเมนต์ยังถูกตัดหลังพูดต่อเนื่อง 4, 5 หรือ 6 วินาที (Fastest, Balanced, Most accurate) แม้ไม่มีช่วงหยุด โดยตัดที่จุดที่เงียบที่สุดใน 1.5 วินาทีสุดท้าย
- **ซ้อนทับ แล้วตัดส่วนซ้ำ** เซกเมนต์ที่ต่อจากการตัดกลางเสียงพูดต่อเนื่องจะเริ่มด้วยเสียงที่เล่นซ้ำ 400 ms เพื่อไม่ให้คำใดถูกตัด จากนั้นตัวรู้จำเสียงจะถอดอักษรช่วงนั้นซ้ำ และส่วนต้นที่ซ้ำจะถูกตัดออกโดยเทียบกับท้ายเซกเมนต์ก่อนหน้า ขั้นตอนนี้ทำกับเซกเมนต์ที่ทราบว่ามีส่วนซ้อนทับเท่านั้น
- **การแยกประโยค** ข้อความที่จบแล้วถูกแยกที่ 。！？ และประโยคที่ยาวเกินประมาณ 34 ตัวอักษรจะถูกแยกที่เครื่องหมายจุลภาค (、) หรือหลังคำเชื่อมที่ยืนเดี่ยวๆ เช่น ので และ けど การแยกเกิดที่ขอบคำเท่านั้น (ผ่าน `Intl.Segmenter`) ชิ้นที่สั้นมากจะถูกรวมกับชิ้นข้างเคียง และวลีที่ยาวจะถูกคงไว้ทั้งก้อนแทนที่จะตัดกลางคัน แต่ละชิ้นกลายเป็นซับไตเติลหนึ่งบรรทัดพร้อมคำขอแปลของตัวเอง
- **การจัดคิวแปล** รันพร้อมกันได้สูงสุดสามคำขอ แต่ละคำขอส่งเฉพาะบรรทัดของตัวเองกับบรรทัดก่อนหน้าไม่กี่บรรทัด (และ glossary ของคุณ) ไม่ใช่ทั้งบทถอดเสียง และบอกโมเดลว่าบรรทัดนั้นต่อเนื่องหรือถูกตัดกลางประโยค ประโยคที่ถูกแยกจึงยังอ่านเป็นธรรมชาติโดยไม่ต้องเขียนบรรทัดที่อยู่บนจอแล้วใหม่ ผลลัพธ์ถูกปล่อยตามลำดับที่พูดแม้ API ตอบกลับสลับกัน คำขอที่ใช้เวลาเกิน 4 วินาทีจะไม่รั้งคำขอหลังๆ อีก และคำแปลไทยของมันจะเติมลงในแถวของตัวเองเมื่อมาถึง
- **ความล้มเหลวมองเห็นได้** บรรทัดที่แปลล้มเหลวจะแสดงข้อความญี่ปุ่น (และ "Translation unavailable" ในประวัติ) แทนที่จะรอตลอดไป

### ข้อความญี่ปุ่นสดจริงๆ แล้วคืออะไร

ผู้ให้บริการแบบ Whisper ส่งผลลัพธ์กลับมาหนึ่งชุดต่อหนึ่งคำขอ และไม่ได้สตรีม ระหว่างที่มีคนพูด Kotoba Live จึง **ถอดเสียงเซกเมนต์ปัจจุบันซ้ำประมาณวินาทีละครั้ง** และแสดงผลเป็นข้อความจางๆ ที่ยังไม่นิ่ง หน้า Settings และ Dashboard บอกเรื่องนี้ไว้ และเซิร์ฟเวอร์รายงาน `interim: "rerun"` ถ้าปิด `ENABLE_PARTIALS` เซิร์ฟเวอร์จะรายงาน `none` และบรรทัดจะปรากฏเมื่อประโยคจบ ผู้ให้บริการที่สตรีมจริงจะรายงาน `native` ซึ่งยังไม่มีในตัว (เพิ่มได้ผ่านอินเทอร์เฟซ `SttProvider` โดยตั้ง `streaming = true`)

การถอดเสียงซ้ำมีข้อจำกัดที่ควรรู้: ท้ายบรรทัดสดอาจเปลี่ยนได้ และฉบับร่างภาษาไทย (ปิดไว้เป็นค่าเริ่มต้น) อาจเปลี่ยนความหมายเมื่อฟังได้มากขึ้น มีเพียงบรรทัดที่จบแล้วเท่านั้นที่ถือว่ายืนยันแล้ว

| อะไร | ที่ไหน |

| เสียงซ้อนทับและ pre-roll | `OVERLAP_MS`, `PREROLL_MS` ใน `server/src/segmenter.ts` |
| จำนวนตัวอักษรต่อซับไตเติล, ขนาดชิ้นต่ำสุด | `DEFAULT_LIMITS` ใน `server/src/sentences.ts` |
| จำนวนการแปลพร้อมกัน, จำนวนบรรทัดบริบท, เวลารอคำขอที่ช้า | ตัวเลือกของ `TranslationScheduler` ใน `server/src/translation-scheduler.ts` |
| เวลาอ่าน, เฟด, เวลาขั้นต่ำบนจอ | `readingMs`, `FADE_MS`, `MIN_SHOW_MS` ใน `web/src/lib/subtitleQueue.ts` |

**ค่าใช้จ่าย**: ข้อความสดจะส่งเซกเมนต์ที่ได้ตอนนั้นซ้ำ เมื่อจำกัดเซกเมนต์ที่ 4 ถึง 6 วินาที จะเบากว่าก่อนหน้านี้ แต่ปริมาณเสียงที่คิดเงิน speech-to-text ยังอยู่ที่ประมาณ 2 ถึง 3 เท่าของปริมาณเสียงพูดจริง ถ้าเรื่องนี้สำคัญ ให้ปิด (`ENABLE_PARTIALS=false`) ใช้ความหน่วงแบบ *Most accurate* หรือใช้โมเดลราคาถูกหรือรันในเครื่อง ตอนนี้แต่ละประโยคเป็นคำขอแปลของตัวเอง จำนวนคำขอแปลจึงมากขึ้นแต่สั้นลงมาก


## ความปลอดภัยและความเป็นส่วนตัว

- API key ถูกอ่านที่ฝั่งเซิร์ฟเวอร์เท่านั้น `/api/health` รายงานเพียงว่าตั้งค่าแล้วหรือยัง ไม่เคยส่ง key
- WebSocket รับคำขอ same-origin บวก `ALLOWED_ORIGINS` ตรวจสอบทุกข้อความด้วย schema จำกัดขนาดเฟรม ปฏิเสธไคลเอนต์ที่สตรีมเร็วกว่าเวลาจริง จำกัดจำนวนการเชื่อมต่อต่อ IP และจำกัดอัตราของ HTTP API
- เสียงถูกเก็บในหน่วยความจำเฉพาะประโยคที่กำลังประมวลผล และไม่เคยถูกเขียนลงดิสก์หรือบันทึก log ไม่มีฟีเจอร์อัดเสียง
- เซิร์ฟเวอร์ผูกกับ `127.0.0.1` เป็นค่าเริ่มต้น ถ้าเปิดให้เข้าถึงจากภายนอก ให้ใช้ HTTPS และตั้ง `ACCESS_TOKEN`
- ผู้ให้บริการของคุณได้รับเสียงและข้อความที่คุณส่งไป ภายใต้นโยบายความเป็นส่วนตัวของเขาเอง

## โครงสร้างโปรเจกต์

## การทดสอบ

`npm test` รันเทสต์ 68 รายการ (เซิร์ฟเวอร์ 31, เว็บ 37):

- **ไปป์ไลน์ฝั่งเซิร์ฟเวอร์** ใช้ตัวรู้จำเสียงที่อ่านเสียงที่ได้รับจริงๆ (หนึ่งตัวอักษรต่อ 100 ms) เสียงที่ซ้อนทับจึงให้ข้อความที่ซ้อนทับ ทดสอบว่า: เสียงพูดต่อเนื่องถูกตัดเป็นเซกเมนต์สั้นโดยไม่มีอะไรหายหรือซ้ำ, ข้อความสดปรากฏก่อนประโยคจบ, การหายใจสั้นๆ จบเซกเมนต์, การแปลที่ช้าไม่รั้งข้อความถอดเสียงถัดไป, คำแปลถูกปล่อยตามลำดับที่พูดแม้ API ตอบสลับกัน, ผลลัพธ์ยาวจากตัวรู้จำเสียงกลายเป็นหลายซับไตเติล และเมื่อหยุดแล้วไม่มี timer หรือคำขอค้างอยู่
- **ข้อความและหน่วยจัดคิว**: การแยกประโยคและวลี, การตัดส่วนซ้ำ, ขีดจำกัดการทำงานพร้อมกัน, คำขอที่ช้าและล้มเหลว, การกำจัดรายการซ้ำ และการคืนทรัพยากรอย่างสะอาด
- **เครือข่าย**: เซสชันเต็มรูปแบบผ่าน WebSocket จริง รวมถึงการตรวจ origin, token และข้อความที่ผิดรูปแบบ
- **ตรรกะฝั่งเว็บ**: history reducer (ลำดับที่พูด, event ที่มาช้า, ข้อความ final ไม่ถูกเขียนทับ), คิวซับไตเติล (การซ้อนสแต็ก, id คงที่, เริ่มนาฬิกาอ่าน, เวลาตามความยาว, กฎเมื่อล้น, โหมดประวัติ, การเฟด, ไม่กลับมาอีก), รูปแบบการส่งออก, การตรวจสอบการตั้งค่า และการวาด canvas ของ video-PiP
- **วงจรชีวิต**: เทสต์ controller ที่ใช้ capture และ WebSocket จำลอง ครอบคลุมการฟัง, event ที่มาไม่เรียงลำดับ, การเชื่อมต่อใหม่ด้วย timestamp ต่อเนื่อง, การหยุด, เบราว์เซอร์ยุติการแชร์ และข้อผิดพลาดโควตา และตรวจว่า **ไม่มี timer ค้างอยู่** หลังจากนั้น
- **UI smoke test** (jsdom): เมื่อเปิด overlay บรรทัดเดโมซ้อนกัน บรรทัดเก่าอยู่ต่อขณะที่บรรทัดใหม่ปรากฏ ออกไปหลังหมดเวลาอ่าน และยังอยู่ในประวัติ
- **Audio worklet**: การรีแซมเปิลและการแบ่งเฟรมที่ 48, 44.1 และ 16 kHz

สิ่งที่เทสต์อัตโนมัติไม่ครอบคลุม: ตัวเลือกแหล่งเสียงและเสียงจากแท็บของเบราว์เซอร์จริง, หน้าต่าง Picture-in-Picture และแอนิเมชันสไลด์ในเบราว์เซอร์จริง, ตัวรู้จำเสียงจริงจัดการเสียงซ้อนทับได้ดีแค่ไหน (การสะกดคันจิหรือคานะต่างกันของตัวอักษรที่ซ้ำอาจเหลือส่วนซ้ำเล็กน้อย) และการเรียกผู้ให้บริการ speech และการแปลจริง สิ่งเหล่านี้ต้องใช้เบราว์เซอร์จริงและ key ของคุณ เช็กลิสต์ด้านล่างเป็นวิธีทดสอบที่เร็วที่สุด

### ตรวจด้วยมือ (ประมาณห้านาที)

1. รัน `npm run dev` เปิดแอปใน Chrome หรือ Edge และเล่นวิดีโอภาษาญี่ปุ่นที่มีเสียงพูดต่อเนื่อง (ทอล์กโชว์หรือ vlog ใช้ได้ดี) ในอีกแท็บ
2. เลือกแท็บนั้นโดยติ๊ก **Also share tab audio** เปิด **In-app overlay** และคลิก **Open PiP window** ลากหน้าต่าง PiP ไปวางทับวิดีโอ
3. สังเกตว่า: ข้อความญี่ปุ่นปรากฏขณะที่ประโยคยังพูดอยู่ (ท้ายข้อความจางลง), ภาษาไทยมาทีละชิ้นสั้นๆ ไม่ใช่ทั้งย่อหน้า, บรรทัดใหม่สุดอยู่ล่างสุดและบรรทัดเก่าสไลด์ขึ้น, บรรทัดเก่าเฟดหลังจากคุณมีเวลาอ่านพอเท่านั้น
4. เปิด **Subtitle History**: ควรมีทุกบรรทัด รวมถึงบรรทัดที่ออกจากจอไปแล้ว ลองส่งออก SRT แล้วตรวจเวลา
5. ใน **Settings** ลองปรับ Visible lines, Subtitle duration และ Keep subtitles longer ตัวอย่างจะอัปเดตทันที
6. คลิก **Stop Listening** และยืนยันว่าตัวบ่งชี้การแชร์ของเบราว์เซอร์หายไป
7. ถ้าบรรทัดถูกตัดเร็วหรือช้าเกินไปสำหรับเนื้อหาของคุณ ให้ปรับค่าความหน่วงก่อน แล้วค่อยปรับค่าในตาราง Tuning

## การแก้ปัญหา

- **"Source has no audio"**: เลือกแท็บของ Chrome และติ๊ก *Also share tab audio*
- **"Can't reach the server"**: ต้องรัน `npm run dev` อยู่ ถ้าเปลี่ยน `PORT` ให้รีสตาร์ททั้งสองโปรเซส
- **Speech หรือการแปล "not set up"**: ตรวจ `.env` แล้วรีสตาร์ทเซิร์ฟเวอร์ หน้า Dashboard แสดงสิ่งที่ตรวจพบ
- **ข้อผิดพลาดโควตาหรือ key**: ข้อความจากผู้ให้บริการถูกบันทึกฝั่งเซิร์ฟเวอร์ เบราว์เซอร์เห็นเพียงสรุปสั้นๆ
- **ซับไตเติลช้า**: เลือกความหน่วง *Fastest* ใช้โมเดล speech ที่เร็วกว่า หรือรันในเครื่อง
- **ข้อความแปลกๆ เมื่อมีเพลง**: แอปตัดสิ่งที่ hallucinate บ่อยที่สุดทิ้ง และหยุดขอข้อความบางส่วนหลังได้ผลว่างซ้ำๆ แต่เพลงประกอบเสียงดังยังลดความแม่นยำอยู่ดี
